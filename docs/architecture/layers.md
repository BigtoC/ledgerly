# Layers (3-Layer Architecture)

> Authoritative source: [`PRD.md` → *Architecture*](../../PRD.md#architecture).

Ledgerly uses a strict **3-layer architecture** (Data → UI), with a `domain/` use-case layer added only in Phase 2. Import-level layer boundaries are enforced by `test/unit/architecture/layer_boundaries_test.dart` (see [`dependencies.md`](./dependencies.md#layer-boundary-check)) for every file under `lib/features/`, plus `lib/core/`, `lib/data/` and use cases. Feature files are covered by name: `*_screen.dart` and `widgets/` follow the widget rule, `*_controller.dart` and `*_providers.dart` the controller rule, `*_state.dart` the state rule, and a catch-all applies the widget rule to every other feature file (for example `analysis/charts/charts_section.dart`, `selected_slice.dart`, `transactions/amount_formula.dart`), so a new feature file is covered without editing the rules. `lib/app/` is covered only by `app_forbids_platform_plugins`, which keeps `package_info_plus`, `path_provider`, `file_picker` and `file_selector` out of every `lib/app/` file except `lib/app/providers/service_providers.dart`, and by `app_widgets_forbid_repository_and_service_providers`, which keeps `repository_providers.dart` and `service_providers.dart` out of `lib/app/widgets/`. `lib/data/seed/`, `lib/main.dart` and the generated `lib/l10n/` are not covered, and the rules below that are not about imports still rely on review.

## Non-Negotiables

- **SSOT on repositories.** Only `data/repositories/*` write to Drift or `flutter_secure_storage`. Controllers and widgets never construct Drift `Insertable` rows, never call DAO `.insert()`, never touch secure storage. Layer-boundary rules are declared in `import_analysis_options.yaml` at the repo root and checked by `test/unit/architecture/layer_boundaries_test.dart`.
- **Drift stays inside repositories.** Repositories map Drift data classes into Freezed domain models in `data/models/` and return those. Controllers and widgets must never see a Drift row type — that is the seam that protects the UI from schema churn.
- **Controllers expose state + commands, not data access.** Each `*_controller.dart` owns an immutable Freezed sealed state (`loading | empty | data(...) | error`) and typed command methods. Widgets read state and call commands; no data transformation in `build()`.
- **Reactive by default.** Repositories return `Stream<T>` backed by Drift `.watch()`; controllers consume via Riverpod `StreamNotifier` / `AsyncNotifier`. Avoid manual refresh patterns.
- **Error propagation is typed.** Services throw typed exceptions, repositories re-throw or wrap, use cases translate to domain failures, controllers expose `AsyncValue`. No `try/catch` in widgets. No unhandled `Future`.

## Where things live

- **App-layer construction** lives in providers: `lib/app/providers/repository_providers.dart` builds the concrete `Drift*Repository` implementations, `AppUpdateRepository` and the use cases, and `lib/app/providers/service_providers.dart` builds the services (`dio`, `exchangeRateService`, `csvFileService`, `packageInfoService`). Under `lib/features/`, only controllers and `*_providers.dart` may import `repository_providers.dart`, and no file may import `service_providers.dart` or `app_database_provider.dart`, so a widget cannot reach a repository, nor a controller a service or `AppDatabase`, through those files. App-level values that widgets read get their own file instead: `exchange_rates_provider.dart` (`exchangeRatesProvider`) and `app_version_provider.dart` (`appVersionProvider`). `appDatabaseProvider` is intentionally a required override from `bootstrap()` or `test/support/test_app.dart` — see [`bootstrap.md`](./bootstrap.md).
- **External I/O** follows the same boundary: services own the calls and repositories own what is done with the results. `lib/data/services/exchange_rate_service.dart` owns the FX Dio calls and `lib/data/repositories/exchange_rate_repository.dart` owns `exchange_rates` persistence/refresh. For app updates, `lib/data/services/app_release_service.dart` owns the Dio calls (GitHub latest-release lookup and APK download) and the `<cache>/updates/` directory the APKs land in, and `lib/data/services/apk_installer_service.dart` owns the `ledgerly/apk_installer` platform channel to Android's `PackageInstaller`; `lib/data/repositories/app_update_repository.dart` orchestrates them (update lookup, SHA-256 verification of the download, install, clean-up). Platform plugins get the same treatment: `lib/data/services/package_info_service.dart` wraps `package_info_plus`, feature files may not import `package_info_plus`, `dio`, `file_picker`, `file_selector` or `path_provider`, and `lib/app/` files other than `service_providers.dart` may not import `package_info_plus`, `path_provider`, `file_picker` or `file_selector`. Widgets/controllers consume `exchangeRatesProvider`, `appVersionProvider`, `availableAppUpdateProvider`, `appUpdateControllerProvider` or repository commands instead of instantiating HTTP clients or calling services.
- **Feature slices co-locate read-only helper providers** for view models and hydration seeds in every `lib/features/**/*_providers.dart` (e.g. `lib/features/home/home_providers.dart`, `lib/features/accounts/accounts_providers.dart`). Like controllers, they may read repositories, domain models and `app/providers/` (except `service_providers.dart`), never `AppDatabase`/DAOs, services or Drift. Prefer slice-local providers over reaching into DB internals from widgets: when a widget needs a one-off repository call, expose it from the slice's `*_providers.dart`, as `txAccountLookupProvider` in `lib/features/transactions/transactions_providers.dart` does for the account picker.
- **`core/` may use domain models, and nothing else from `data/`.** It may import Flutter/SDK packages and the plain domain models in `data/models/` (for example `lib/core/utils/money_formatter.dart` takes `Currency` for its `decimals`), but never repositories, services, `AppDatabase`/DAOs, seed data, use cases, features or `app/` ([`PRD.md` → *Layer Boundaries*](../../PRD.md#layer-boundaries-forbidden-imports)).
- **`domain/` exists only in Phase 2.** MVP is primarily `app/`, `core/`, `data/`, `features/`. The exceptions are the use cases in `lib/data/use_cases/`: `recurring_generation_use_case.dart` (the recurring-rules generation engine) and `csv_import_use_case.dart` (Fortune City CSV import). They live in `data/` because each coordinates several repositories inside one atomic `db.transaction` rather than crossing layered boundaries.

## Chart slice — concrete example of the seam

The drill-down on the Analysis tab is the clearest example of how UI-layer state is kept out of the data layer:

- Selection identity lives in `lib/features/analysis/charts/selected_slice.dart` (`SelectedSlice.category | account | currency`), held by `lib/features/analysis/charts/charts_selection_controller.dart`.
- `lib/features/analysis/charts/charts_controller.dart` translates the active selection into plain `{categoryId, accountId, currencyCode}` filters before calling the repository — the data layer never sees `SelectedSlice`.
- `lib/features/analysis/charts/slice_drilldown_controller.dart` owns the selected-slice row stream plus the delete/undo lifecycle.
